# svc-digest

## Что это

Автономный новостной дайджест для одного человека (Влад). Собирает RSS, ИИ
отбирает под `interests.md`, шлёт дайджест в Telegram дважды в сутки — утром в
08:30 и вечером в 20:30 — от имени `@vlad_burba_bot`. Создан на уроке 6.09,
работает на `vlad-main` с 2026-07-26; конвейер перестроен 2026-08-11.

Форма универсальна: источник и задача подставляются. Следующий кандидат —
вакансии для проекта career-shift.

## Технологии

- Python 3.12, `feedparser`, `httpx[socks]`, `python-dotenv`, `tzdata`
- SQLite (файл `digest.db`, без сервера БД)
- OpenRouter API — отбор и выжимки
- Docker (батч-контейнер), cron на хосте

## Архитектура — три работы, развязка через базу

Три независимых прогона одного образа:

- **СБОРЩИК** `python digest.py collect` — cron раз в час. RSS → дедуп по всей
  базе → запись со статусом `new`. **ИИ не зовёт вообще** → заход бесплатен.
  **В чат не пишет никогда.**
- **ФИЛЬТР** `python digest.py filter` — cron 08:00 и 20:00. `expire_old` →
  `get_pool` пакетом (новые + очередь) → ИИ-отбор в два шага → `pending`,
  `rejected` или `queued`.
  Единственная работа, которая тратит квоту OpenRouter. **В чат не пишет** —
  провал человек увидит строкой в футере ближайшего дайджеста.
- **ОТПРАВИТЕЛЬ** `python digest.py send` — cron 08:30 и 20:30. `get_pending` →
  рендер → Telegram → `mark_sent` с `message_id`. **Сигнал в любом исходе** —
  единственная часть, которая говорит с человеком.

Смысл: отправка зависит только от живости Telegram, не от RSS и ИИ.

### Почему ИИ вынесен из сборщика (решение 2026-08-11)

Квота OpenRouter — **50 запросов в сутки на АККАУНТ**, и она общая с проектом
`vladburba-bot` (ключи разные, аккаунт один). Ежечасный отбор съедал 7–16
запросов в сутки, причём вхолостую: 11 августа четыре захода потревожили модель
ради одной статьи, а девять заходов не нашли ничего нового вовсе.

Стало: **2 запроса в сутки, максимум 6** (два окна × три звена цепочки при
полном невезении). Боту гарантированно остаётся 44+ из 50 — и это следует из
устройства, а не из наблюдения. Поэтому общий счётчик квоты на два проекта
(числился техдолгом у бота) решено **не делать**: он лечил бы проблему, которой
после перестройки нет. Вернуться к нему стоит, если у ключа появится третий
потребитель.

Второй выигрыш важнее экономии: модель теперь видит весь накопленный день сразу
и выбирает лучшее, а не судит одну статью в вакууме.

Карта конвейера — `СХЕМА.md` (Mermaid). **Правится вместе с кодом**: меняешь
конвейер — обновляешь схему в том же коммите.

## Структура

- `digest.py` — точка входа, три команды, логирование на каждом стыке;
  `BATCH_LIMIT=40` (потолок пакета фильтра), `MAX_MESSAGES=1` (потолок отправки —
  одно сообщение, то есть пять новостей за выпуск)
- `collect.py` — RSS через feedparser, окно 168 часов (неделя, запас на простой)
- `dedup.py` — нормализация ключа «та же статья»: номер статьи вместо адреса,
  устойчива к переезду между блогами и к UTM-хвостам
- `filter_ai.py` — OpenRouter, цепочка моделей с фолбэком при 429/503;
  `stats["attempts"]` — сколько запросов реально ушло, включая провальные
- `database.py` — схема `news` (natural key, статусы `new`/`pending`/`sent`/
  `rejected`/`expired`), `collect_runs` (воронка сбора) и `filter_runs` (журнал
  отбора: пакет, вердикт, модель, расход квоты); `filter_unseen` дедуплицирует
  по **всей** базе независимо от статуса
- `render.py` — текст дайджеста, по 5 новостей в сообщении, потолок 1 сообщение;
  шапка 🌅/🌆 по времени суток, футер с честным периодом и строкой фильтраций
- `telegram.py` — отправка, outbox с `message_id`
- `netcfg.py` — единственная точка, где читается `EGRESS_PROXY`
- `clock.py` — `LocalFormatter`: в базе всегда UTC, человеку всегда MSK
- `bench_models.py` — замер моделей, в рабочий контур не входит
- `interests.md` — config-as-code: иерархия из 10 приоритетов (1 — ИИ в
  эксплуатации, 2 — Anthropic и Claude), потолок **5 новостей за окно** и
  живые примеры из ручной разметки. Модель ранжирует по нему, а не фильтрует

## Команды

```bash
python digest.py collect                    # локально, из .venv
python digest.py filter                     # тратит квоту OpenRouter!
python digest.py send                       # утренний: при пустой очереди шлёт heartbeat
python digest.py send --quiet-if-empty      # вечерний: при пустой очереди молчит

docker compose run --rm digest collect      # то же в контейнере
docker compose run --rm digest filter
docker compose run --rm digest send
docker compose run --rm digest send --quiet-if-empty

python database.py                          # состояние базы по статусам
```

## PROD

- Сервер `vlad-main` (адрес — в личных заметках, не в репозитории),
  путь `/opt/apps/svc-digest`
- Расписание `/etc/cron.d/svc-digest` от `root` (время сервера = MSK):

  | когда | что | зачем |
  |---|---|---|
  | `5 * * * *` | `collect` | копит `new`, ИИ не трогает — бесплатно |
  | `0 8 * * *` | `filter` | разбор ночного накопления, за 30 мин до отправки |
  | `30 8 * * *` | `send` | 🌅 утренний дайджест, heartbeat при пустоте |
  | `0 20 * * *` | `filter` | разбор дневного накопления |
  | `30 20 * * *` | `send --quiet-if-empty` | 🌆 вечерний, при пустоте молчит |

- Bind-mount'ы: `digest.db`, `digest.log`, `interests.md`
- Логи: `digest.log` (сервис) и `cron.log` (вывод cron)
- **Код на PROD лежит без git** (файлы залиты вручную) — деплой копированием,
  а не `git pull`. Отличие от `vladburba-bot`, где на сервере рабочая копия.

## Грабли — проверено на этом проекте, не переоткрывать

1. **`network_mode: host` обязателен.** Из bridge-NAT контейнер не достаёт до
   `habr.com` (РФ IP) — SYN не доходит, при том что telegram и openrouter из
   bridge работают, а хост берёт habr за 1.6 с. Policy-routing ни при чём —
   квирк NAT/netns.
2. **Весь egress на сервере — через прокси.** Напрямую из контейнера работает
   только Telegram: habr виснет, openrouter отдаёт 403 (блок IP дата-центра).
   `EGRESS_PROXY=socks5://127.0.0.1:1080` — тот же Xray, что у бота (урок 5.09).
   Локально на маке переменная пустая: с мака всё доступно напрямую.
3. **`digest.db` и `digest.log` должны существовать до первого `run`** — иначе
   Docker создаст на их месте директории (грабля с урока 5.12). На сервере —
   `touch` перед стартом.
4. **`tzdata` в зависимостях не случайно.** `ZoneInfo("Europe/Moscow")` в
   python:3.12-slim работает, но Debian-slim базу зон не гарантирует — без неё
   сервис падал бы на импорте, то есть дайджест молча пропал бы.
5. **Проверять доступность источника нужно из контейнера, а не с хоста.** На
   деплое 6.09 проверка с хоста показала «всё ок», а из контейнера habr был
   недоступен — отладка заняла заметно дольше самого деплоя.
6. **Развязали работы во времени — проверь, что данные это переживут.** При
   выносе ИИ в отдельную работу (2026-08-11) чуть не потеряли текст новости:
   `summary` из ленты жил только в памяти прогона, потому что сбор и отбор были
   одним процессом. Стали разными — текст обязан лежать в базе. Общее правило:
   разрывая шаг на два, перечисли всё, что раньше передавалось «по воздуху».
7. **Схему боевой базы двигает только `ALTER` в `init_db`.** `CREATE TABLE IF
   NOT EXISTS` накрывает пустую базу и молча пропускает существующую — новые
   колонки в проде не появятся. Миграция обёрнута в try/except на «duplicate
   column», потому что `init_db` зовётся каждым заходом, то есть раз в час.
8. **Индекс по новой колонке создавать ПОСЛЕ `ALTER`, а не в `SCHEMA`.** На
   пустой базе разницы нет, на боевой — падение `no such column`: таблица уже
   существует, `CREATE TABLE IF NOT EXISTS` её пропускает, и `CREATE INDEX` из
   того же скрипта выполняется раньше, чем колонка появится. Поймано на копии
   прода 2026-08-12 — ровно то, ради чего миграции и проверяются на копии.
9. **Ключ дедупликации — номер статьи, а не её адрес.** Habr переносит статью
   между корпоративными блогами, и URL меняется целиком
   (`/companies/yandex_cloud_and_infra/articles/1068692/` →
   `/companies/yandex/articles/1068692/`), а номер остаётся. По адресу такая
   статья выглядит новой и приходит в дайджест второй раз — поймано 2026-08-11
   на позициях 5 и 6 одного сообщения. Нормализация живёт в `dedup.py`, в базе
   отдельная колонка `dedup_key`. **Добавляя новый источник — проверь, что у
   него считается за идентификатор**, иначе грабля повторится на его ленте.
10. **Одного уровня дедупа мало.** Через неделю после фикса №9 дубль пришёл
   снова, но по другой причине: один и тот же текст вышел под ДВУМЯ номерами
   (`1071572` и `1071582`, «DSL позволяют надежно использовать LLM»,
   18.08.2026). Номерной дедуп такое пропускает честно — статьи разные.
   Добавлен второй уровень: нормализованный заголовок за последнюю неделю
   (`dedup.title_key`). Окно недельное намеренно — по всей базе за годы
   накопятся законные совпадения вроде «Дайджест новостей», и второй уровень
   начнёт глушить свежее.

### Отбор двухшаговый, очередь конкурирует (2026-09-21)

Раньше у статьи было два исхода: взяли или отвергли навсегда. Хорошая статья,
не попавшая в пятёрку, выбывала — это и было главной потерей.

Теперь исходов три. Модель называет **взятых** (до потолка, по важности) и
**мимо интересов**; всё, что она не назвала, получает статус `queued` и в
следующем окне конкурирует со свежими на равных. В урожайный день сильный
материал подождёт, в пустой — выйдет вперёд.

Отборы независимы: в 08:00 и 20:00 фильтр смотрит только на то, что есть
сейчас, и ничего не знает про «сутки». Это и позволило делать честную
диагностику — в ней нет чисел из разных временных окон.

**Диагностика уходит отдельным сообщением** после дайджеста. Четыре попытки
уместить её в футер провалились: числа из разных очередей и моментов времени
оказывались рядом, читатель их складывал, они не сходились. Вывод — сообщение
с новостями должно быть про новости.

Статистика по моделям копится в `model_attempts` **за всё время**, по строке
на каждое обращение. Восстанавливать её задним числом из `filter_runs` нельзя:
состав цепочки меняется, и новой модели приписались бы чужие отказы.

### Критерии отбора выверены разметкой (2026-08-21)

Влад вслепую оценил 60 новостей за неделю: 41 «оставить», 12 «мимо», 7 «не
уверен». Сверка с решениями модели показала обратное ожидаемому — **ложных
срабатываний ноль**, ложных пропусков 16. Отбор был не широким, а узким:
запреты «рынок и бенчмарки», «академические работы», «распознавание речи»
резали нужное (цены подписок, сжатие моделей, поиск по голосу).

Отсюда два вывода, зафиксированных в `interests.md`:

- **Ужесточать критерии было бы ошибкой.** Проблема объёма решается не
  запретами, а ранжированием: потолок 5 за окно и явная иерархия тем.
- **Примеры сильнее формулировок.** В файл вложены 22 одобренных и 12
  забракованных заголовка живьём — модель следует им точнее, чем описаниям.

Проверка после правки: два пакета по 30 новостей, выбрано 5 и 5, **все десять
попали в «оставить»**, промахов ноль. Прежнее совпадение с человеком — 70%.

Повторить замер просто: выборка собирается запросом к базе, разметка идёт
через страницу-картотеку, результат сравнивается со статусами `sent`/`rejected`.

## Особенности работы

- **Недоделки этого проекта — в общем реестре `infra/техдолг.md`.** Там единая точка
  правды по всем проектам и серверам; вопрос «что тут осталось» — сначала туда.
- Токен `BOT_TOKEN` общий с `vladburba-bot`. Известный техдолг: развязать, чтобы
  инцидент в одном сервисе не задевал второй (занесён в реестр).
- Расширение источников — по одному, с проверкой доступности из контейнера.
