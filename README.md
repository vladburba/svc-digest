# svc-digest

Персональный новостной дайджест: тянет RSS, отдаёт накопленное языковой модели,
та отбирает интересное — и дважды в сутки присылает выжимку в Telegram.

Работает в продакшене с 26 июля 2026 года, каждый день, без ручного участия.
Стоит **0 ₽ в месяц**: бесплатные модели через OpenRouter, дневная квота
расходуется на два запроса.

Проект писался как личный инструмент, но устройство универсальное — источник и
критерии отбора задаются конфигом, код не меняется.

## Как это выглядит

Утреннее сообщение в Telegram:

```
📰 🌅 Утренний дайджест · 20 сентября

1. ИИ-агенту запретили запись в CRM. Но CRM всё равно изменилась
   Исследовали случай, когда агенту запретили запись, но система всё
   равно изменила данные из-за побочных эффектов runtime-контроля.
   читать

2. Все числа на месте, а смысл изменился: как проверять правки ИИ
   Разобрал, почему автоматическая сверка чисел не выявляет смысловые
   искажения после правки ИИ.
   читать

   …ещё три новости

📬 В этом дайджесте 5 новостей
🤖 Отбор: в 08:00 — из 14 выбрал 5
```

Выжимку под каждым заголовком пишет модель, ссылку берёт не она, а код —
по номеру из списка. Это сделано намеренно: так модель физически не может
подсунуть выдуманный URL.

## Задача, вокруг которой всё построено

Бесплатные модели OpenRouter дают **50 запросов в сутки на аккаунт**. Это
немного, и лимит легко проесть впустую.

В первой версии отбор жил внутри сборщика: раз в час сходил за лентой, тут же
спросил модель. Замер показал 7–16 запросов в сутки, причём большей частью зря —
модель звали ради одной-двух свежих статей, а однажды четыре захода подряд
потревожили её ради единственной заметки, которую она же и забраковала.

Решение — развязать работы во времени:

| работа | ритм | тратит квоту |
|---|---|---|
| **сбор** | раз в час | нет |
| **отбор** | 08:00 и 20:00 | **да** |
| **отправка** | 08:30 и 20:30 | нет |

Сбор стал бесплатным и частым, отбор — редким и пакетным. Расход упал до
**2 запросов в сутки, максимум 6** — и это не наблюдение, а свойство
конструкции: окон ровно два, длина цепочки моделей — три.

Второй выигрыш оказался важнее экономии. Раньше модель оценивала статью в
одиночку: «подходит или нет». Теперь она получает весь накопленный день одним
списком и **выбирает лучшее из имеющегося** — это принципиально другая задача,
и решает она её заметно точнее.

## Устройство

Три независимые программы, которые общаются только через SQLite. Никто никого
не вызывает напрямую: один записал, другой позже прочитал.

```
RSS ──► сбор ──► [new] ──► отбор ──► [pending] ──► отправка ──► Telegram
      раз в час          08:00/20:00            08:30/20:30
                              │
                              └──► [rejected] / [expired]
```

Смысл развязки: к моменту отправки дайджест уже лежит готовым. Упала лента
ночью — сборщик подберёт через час. Не ответила модель утром — вечернее окно
разберёт накопленное, и выпуск не будет пустым.

Полная карта с диаграммами — в [`СХЕМА.md`](СХЕМА.md), включая жизненный цикл
записи и таблицу принятых решений с обоснованиями.

## Как отбирает

Критерии живут в [`interests.md`](interests.md) — обычным текстом, без кода.
Файл примонтирован в контейнер, правки применяются без пересборки.

Внутри три части:

1. **Потолок.** «Выбери не больше 5» — модель обязана ранжировать, а не
   фильтровать. Это единственный способ совместить «мне интересно почти всё» с
   «читать готов десяток в день».
2. **Иерархия тем** — десять пунктов по убыванию важности. Когда подходящего
   больше потолка, выигрывает то, что выше.
3. **Живые примеры** — по два десятка реальных заголовков «такое нужно» и
   «такое мимо».

Примеры взялись не из головы. Владелец вслепую разметил 60 новостей за неделю,
не видя решений модели; сверка показала, что критерии были **уже** его вкуса —
ноль лишних присланных статей и шестнадцать зря выброшенных. После правки
контрольный прогон на той же выборке дал десять попаданий из десяти.

Способ воспроизводимый и лежит в репозитории — см. [`eval/`](eval/): сбор
выборки из базы, страница для слепой разметки, подсчёт и сравнение замеров.
Повторять стоит после каждого заметного изменения критериев или модели, иначе
«стало лучше» остаётся ощущением.

## Запуск у себя

Нужны: Python 3.12, ключ [OpenRouter](https://openrouter.ai) (бесплатный),
бот от [@BotFather](https://t.me/BotFather) и ваш Telegram chat_id.

```bash
git clone <этот-репозиторий> && cd svc-digest
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env     # вписать ключ, токен бота и chat_id
$EDITOR interests.md     # описать, что вам интересно

python digest.py collect   # собрать ленту — бесплатно, модель не трогает
python digest.py filter    # отобрать — тратит квоту OpenRouter
python digest.py send      # отправить в Telegram
python database.py         # посмотреть состояние базы
```

Источник задаётся в `collect.py` (по умолчанию — хаб «Искусственный интеллект»
на Хабре).

### В Docker

Контейнер не демон, а батч: поднимается на один прогон и умирает.

```bash
touch digest.db digest.log        # ОБЯЗАТЕЛЬНО до первого запуска,
                                  # иначе Docker создаст на их месте папки
docker compose run --rm digest collect
docker compose run --rm digest filter
docker compose run --rm digest send
```

### По расписанию

Готовый файл — [`svc-digest.cron`](svc-digest.cron), кладётся в `/etc/cron.d/`.
Пять строк: сбор ежечасно, отбор дважды, отправка дважды.

## Структура

| Файл | Что делает |
|---|---|
| `digest.py` | точка входа, три команды: `collect`, `filter`, `send` |
| `collect.py` | RSS через feedparser, окно 168 часов |
| `dedup.py` | ключ «та же статья»: по номеру статьи, а не по адресу |
| `filter_ai.py` | запрос к OpenRouter, цепочка моделей с фолбэком |
| `database.py` | SQLite: статусы записей и журналы обеих работ |
| `render.py` | вёрстка сообщения, разбивка на части, футер |
| `telegram.py` | отправка, запись `message_id` как расписки |
| `netcfg.py` | единственная точка, где читается прокси |
| `clock.py` | время: в базе всегда UTC, человеку всегда местное |
| `interests.md` | критерии отбора обычным текстом |
| `СХЕМА.md` | карта конвейера и таблица решений |

## Что внутри может пригодиться

Проект небольшой, но несколько решений вытащены из реальных поломок и описаны
в `CLAUDE.md` вместе с причинами:

- **Дедупликация по номеру статьи, а не по ссылке.** Хабр переносит статьи
  между корпоративными блогами, URL меняется целиком — и статья приходит второй
  раз. Второй уровень, по заголовку за неделю, ловит случай, когда один текст
  опубликован под двумя разными номерами.
- **Модель возвращает номер, а не ссылку** — защита от выдуманных URL.
- **Цепочка моделей от разных провайдеров.** Четыре модели одного провайдера —
  иллюзия защиты: при его перегрузке все четыре ответят отказом одновременно.
- **Текст новости хранится в базе.** Когда сбор и отбор разнесли по времени,
  текст из ленты перестал доживать до модели — он существовал только в памяти
  одного процесса.
- **Миграции проверяются на копии боевой базы.** `CREATE TABLE IF NOT EXISTS`
  молча пропускает существующую таблицу, и новая колонка в проде не появляется;
  индекс по такой колонке падает раньше, чем `ALTER` успеет отработать.

## Состояние

Работает ежедневно. Известные недоделки, которые чинятся:

- Первая модель цепочки иногда возвращает рассуждения вместо чистого JSON —
  разборщик этого не переживает, и окно отбора пропускается. Примерно раз в
  три дня.
- Третья модель цепочки стабильно отвечает отказом и по факту бесполезна.
- Источник пока один.
