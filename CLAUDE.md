# svc-digest

## Что это

Автономный новостной дайджест для одного человека (Влад). Собирает RSS, ИИ
отбирает под `interests.md`, шлёт один дайджест в Telegram в 08:30 от имени
`@vlad_burba_bot`. Создан на уроке 6.09, работает на `vlad-main` с 2026-07-26.

Форма универсальна: источник и задача подставляются. Следующий кандидат —
вакансии для проекта career-shift.

## Технологии

- Python 3.12, `feedparser`, `httpx[socks]`, `python-dotenv`, `tzdata`
- SQLite (файл `digest.db`, без сервера БД)
- OpenRouter API — отбор и выжимки
- Docker (батч-контейнер), cron на хосте

## Архитектура — producer/consumer, развязка через базу

Два независимых прогона одного образа:

- **СБОРЩИК** `python digest.py collect` — cron раз в час. RSS → дедуп по всей
  базе → ИИ-отбор → запись `pending` / `rejected`. **В чат не пишет никогда** —
  при ретрае раз в час завалил бы уведомлениями.
- **ОТПРАВИТЕЛЬ** `python digest.py send` — cron 08:30. `get_pending` → рендер →
  Telegram → `mark_sent` с `message_id`. **Сигнал в любом исходе** — это
  единственная часть, которая говорит с человеком.

Смысл: отправка в 08:30 зависит только от живости Telegram, не от RSS и ИИ.

Карта конвейера — `СХЕМА.md` (Mermaid). **Правится вместе с кодом**: меняешь
конвейер — обновляешь схему в том же коммите.

## Структура

- `digest.py` — точка входа, обе команды, логирование на каждом стыке
- `collect.py` — RSS через feedparser, окно 168 часов (неделя, запас на простой)
- `filter_ai.py` — OpenRouter, цепочка моделей с фолбэком при 429/503
- `database.py` — схема `news` (natural key, статусы pending/sent/rejected) и
  `collect_runs` (воронка прогонов); `filter_unseen` дедуплицирует по **всей**
  базе независимо от статуса
- `render.py` — текст дайджеста, по 5 новостей в сообщении, потолок 5 сообщений
- `telegram.py` — отправка, outbox с `message_id`
- `netcfg.py` — единственная точка, где читается `EGRESS_PROXY`
- `clock.py` — `LocalFormatter`: в базе всегда UTC, человеку всегда MSK
- `bench_models.py` — замер моделей, в рабочий контур не входит
- `interests.md` — config-as-code, критерии отбора обычным текстом

## Команды

```bash
python digest.py collect          # локально, из .venv
python digest.py send
docker compose run --rm digest collect   # в контейнере
docker compose run --rm digest send
```

## PROD

- Сервер `vlad-main` (<IP-сервера>), путь `/opt/apps/svc-digest`
- Расписание `/etc/cron.d/svc-digest` от `root`: `5 * * * *` сбор,
  `30 8 * * *` отправка
- Bind-mount'ы: `digest.db`, `digest.log`, `interests.md`
- Логи: `digest.log` (сервис) и `cron.log` (вывод cron)

## Грабли — проверено на этом проекте, не переоткрывать

1. **`network_mode: host` обязателен.** Из bridge-NAT контейнер не достаёт до
   `habr.com` (РФ IP) — SYN не доходит, при том что telegram и openrouter из
   bridge работают, а хост берёт habr за 1.6 с. Policy-routing ни при чём —
   квирк NAT/netns.
2. **Весь egress на сервере — через прокси.** Напрямую из контейнера работает
   только Telegram: habr виснет, openrouter отдаёт 403 (блок IP дата-центра).
   `EGRESS_PROXY=socks5://127.0.0.1:1080` — тот же Xray, что у бота (урок 5.09).
   Локально на маке переменная пустая: с мака всё доступно напрямую.
3. **`digest.db` и `digest.log` должны существовать до первого `run`** — иначе
   Docker создаст на их месте директории (грабля с урока 5.12). На сервере —
   `touch` перед стартом.
4. **`tzdata` в зависимостях не случайно.** `ZoneInfo("Europe/Moscow")` в
   python:3.12-slim работает, но Debian-slim базу зон не гарантирует — без неё
   сервис падал бы на импорте, то есть дайджест молча пропал бы.
5. **Проверять доступность источника нужно из контейнера, а не с хоста.** На
   деплое 6.09 проверка с хоста показала «всё ок», а из контейнера habr был
   недоступен — отладка заняла заметно дольше самого деплоя.

## Особенности работы

- Токен `BOT_TOKEN` общий с `vladburba-bot`. Известный техдолг: развязать, чтобы
  инцидент в одном сервисе не задевал второй.
- Расширение источников — по одному, с проверкой доступности из контейнера.
